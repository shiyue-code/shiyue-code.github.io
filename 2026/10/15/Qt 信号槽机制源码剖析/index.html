Qt 信号槽机制源码剖析

Qt 信号槽机制源码剖析

信号槽链路就三步：moc 翻译 → connect 登记 → activate 分发。用”公告订阅”模型理解：connect 是在发布者的登记本上记订阅，emit 是发公告，同线程当面喊（同步调用），跨线程寄信到对方的事件队列（异步）。下面贴出的都是真实源码（Qt5，略去无关样板），配中文注释对照理解。

1. “关键字”全是宏（qobjectdefs.h）

宏 展开结果
signals / slots public——信号槽都是普通成员函数
emit 空，纯标记
SIGNAL(a) / SLOT(a) "2" #a / "1" #a，前缀区分信号与槽，运行时查表用

Q_OBJECT 宏只声明了 staticMetaObject、metaObject()、qt_metacast()、qt_metacall()，实现由 moc 在 moc_xxx.cpp 生成——漏写 Q_OBJECT 或没跑 moc，就报 undefined reference to vtable。需要 moc 的根本原因：C++ 没有反射，”哪个函数叫 valueChanged”要靠代码生成补出来。

2. moc 生成物（moc_MyObject.cpp）

① 说明书：元数据表

QT_MOC_LITERAL(idx, ofs, len) 是什么：它把 stringdata0 里的一段字符包装成一个静态 QByteArrayData 头——idx 是 data[] 数组序号，ofs 是字符串在 stringdata0 里的偏移，len 是长度。如 QT_MOC_LITERAL(1, 9, 12) 即”第 9 字节起的 12 字节” → "valueChanged"。它存的是从自身到字符串的相对偏移而非指针：整张表可直接进只读段，加载时无需指针重定位。整数表方法行的第一个数字就是这里的 idx。

这两张表是怎么从类声明生成的

拿 void valueChanged(int value) 走一遍 moc 的”抄写”过程。

第一步，收集名字进字符串表。moc 把类里出现的每个名字——类名、方法名、参数名——按顺序拼进一串 \0 分隔的字符：

每个名字配一行 QT_MOC_LITERAL(idx, 偏移, 长度) 指过去。这三个数字是 moc 扫描时按两条简单规则算出来的：

  • idx = 进表顺序号：按”类名 → 每个方法的（方法名 → tag 占位 → 参数名）”的顺序收集名字，谁先谁编号靠前。所以是 MyObject(0) → valueChanged(1) → ""(2) → value(3) → onValueChanged(4)；
  • ofs = 累加偏移：每个名字紧贴上一个名字排布，中间隔一个 \0——ofs(i+1) = ofs(i) + len(i) + 1，即 0 →(+8+1)→ 9 →(+12+1)→ 22 →(+0+1)→ 23 →(+5+1)→ 29；len 就是名字的字节长度。

另外 moc 会去重：onValueChanged 的参数同样叫 value，直接复用 idx 3 不再重复存；两个方法的 tag 都复用 idx 2 的空串——这就是为什么 5 个 QT_MOC_LITERAL 覆盖了 7 处引用。

onValueChanged 同理，方法行 4, 1, 27, 2, 0x0a——名字 idx 4，标记 0x0a = 槽|public。

编号规则：moc 输出时信号永远排在槽前面（与头文件里区块的书写顺序无关），组内按声明顺序排号；signalCount = 1 就是说”方法列表前 1 个是信号”。所以 valueChanged 是第 0 号方法（且 < signalCount，是信号）——信号 stub 里调的是 activate(this, mo, 0, _a)，qt_static_metacall 里 case 0 也是它。

为什么非要生成这两张表

因为信号槽的设计目标是编译期彻底解耦：发信号的类不知道接收者是谁，甚至不知道有没有人接收——Qt 框架必须在运行期”按名字/编号”找到并调用一个它编译期根本没见过的函数。而 C++ 编译后不保留任何函数名与签名信息（没有反射），只能靠 moc 在构建期把这些信息固化成常量表。

有了表，运行期能力才成立：字符串版 connect 按名查方法、invokeMethod/QML/脚本动态调用、Queued 模式按参数类型 id 深拷贝（第 5 节）、dumpObjectInfo 打印对象结构。可以说这两张表就是 Qt 的”穷人版反射系统”。

编号坐标系：名字/指针是怎么变成下标的

Qt 的方法编号是全继承链统一编号：祖先类的方法占低位，methodOffset() = 祖先方法总数 = 本类方法的起始号。connect 解析出方法后，拆成两半存进 Connection：

  • method_relative：槽在真正声明它的那个类里的局部号（switch 的 case 就是局部号）
  • method_offset：该类的继承偏移——调用时 method_offset <= receiver->metaObject()->methodOffset() 这条检查用来防”对象析构到一半”的状态

三种”东西 → 编号”的解析方式：

  • 字符串版：indexOfMethod(rmeta, "onValueChanged(int)") 沿 superdata 链在字符串表/整数表里按签名匹配；命中后 while (idx < rmeta->methodOffset()) rmeta = rmeta->superClass() 回退到声明该方法的类的元对象——所以存的 callFunction 是声明类的 qt_static_metacall；
  • 指针版：qt_static_metacall 的 IndexOfMethod 分支直接比较函数指针，编译期拿到编号；
  • 信号编号：indexOfSignal 得到 signal_index——它就是 sender 连接表 signalVector 的数组下标，activate 里 at(signal_index) 一次寻址拿到该信号的全部订阅。

要点：

  • AutoConnection 在 emit 瞬间判定（比当前线程与缓存的 receiverThreadData），与 connect 写在哪无关；Direct 路径本质是同步回调，开销等同普通函数调用；
  • 参数寻址靠 _a[] 这套通用约定：_a[0] 是返回值槽位，_a[1..n] 依次是各参数实体地址；switch case 里 (*reinterpret_cast<int*>(_a[1])) 把 void* 强转回具体类型再传给成员函数。框架层于是不需要知道参数具体类型也能搬运——类型信息在元数据表里，强转在 moc 生成的 case 里，跨线程拷贝由 QMetaType 完成。

5. 跨线程：把调用打包成信（qobject.cpp）

寄信：queued_activate

复印参数是关键：emit 返回后原参数即销毁，必须随信寄出副本——这也是 qRegisterMetaType 存在的原因。

收信：receiver 线程的事件循环取出执行

推导出的坑：

现象 原因
槽永不执行 receiver 线程事件循环没在跑，信堆在队列里
槽里拿到野指针 跨线程传指针——复印件只复制值，指针指向的对象不跟着复制
Cannot queue arguments of type 自定义类型没 qRegisterMetaType，无法复印

deleteLater() 也是同一机制：寄一封 DeferredDelete 信给自己，事件循环收到后 delete——跨线程销毁对象请用它。

6. 五种连接方式速查

类型 行为
AutoConnection（默认） emit 时判定：同线程 Direct，跨线程 Queued
DirectConnection 发送者线程内同步调槽
QueuedConnection 打包 QMetaCallEvent 投递，异步执行
BlockingQueuedConnection 同上 + QSemaphore 阻塞等回执
UniqueConnection 修饰位，connect 时查重

其他：QObject 析构自动摘除所有连接；连接表有锁保护（Qt6 用 OrderedMutexLocker 防 ABBA 死锁）；槽执行中 receiver 被删是安全的。

一句话总结：moc 生成”说明书 + 信号 stub + 接线员”，connect 在 sender 的 Connection 链表记订阅，emit 时 activate 按线程亲和性分发——同线程直接调 qt_metacall，跨线程打包 QMetaCallEvent 交给对方事件循环接力。
